# Confirmed contract fixes after checkpoint 8c39c268

Scope: F1/F6 together, F2, Turkish number display, and tracking deployment DB-role hardening. The persistent identity / definition / publication / report / actual revision architecture is retained.

## Versioned definition interpretation (F1/F6)

- Historical publications with `activity_contract_version=1.0`, or no marker, retain the exact v1 builder. Missing `definition_contract_version` has those original semantics.
- New publications store `activity_contract_version=2.0` and `definition_contract_version=2.0`. New immutable definition JSON also stores `definition_contract_version=2.0`; report revisions pin the selected publication's contract version.
- V2 uses an indicator's non-blank calculation method/data source, otherwise the matching ReportCard's values from the **frozen publication**, never today's live card.
- Creating/validating bindings and reading report definitions dispatch by the selected publication's stored version. Unsupported or inconsistent markers are rejected.
- Old publication JSON, hashes, bindings and definition JSON/hashes are not rewritten. A card change affecting the effective method/source creates a new definition and appears in the existing rebase diff view.
- `tests/fixtures/activity_contract_v1_checkpoint.json` was generated by executing the service implementation from exact commit `8c39c268bea7ce0ff85277acec3047a34363f6c3` against the standard sample data. It is checked in so regression tests do not depend on the current builder or Git availability.

## Correction reason after approval (F2)

- API and HTML forms accept `revision_reason`. A non-blank reason is required whenever the predecessor is approved, whether the base publication changes or stays the same.
- Initial report creation and rebasing an unapproved draft do not acquire that requirement.
- The reason is trimmed and preserved on the new immutable ActivityReportRevision, included in its audit event, and displayed in detail/history screens. The predecessor and its actual/evidence history remain untouched.
- Additive migration `a7c2d3e4f5a6` adds the reason with an empty historical default via direct ALTER; existing SQLite/PostgreSQL immutability triggers are retained. A separate insertion trigger also requires a reason for corrections of approved predecessors. No historical UPDATE/backfill is performed.

## Turkish presentation

- Target, actual, numeric deviation, editable actual input and target difference cells use the existing Decimal-based Turkish formatter.
- Examples: `12500` → `12.500`; `12500.23` → `12.500,23`; `1.75` → `1,75`.
- API decimal strings and database Numeric/Decimal values retain their original values; no float conversion is introduced by formatting.
- Tests cover integer, decimal, zero, negative and 26-digit values. The large-number storage/screen integration case uses PostgreSQL because SQLite Numeric is not an exact store at that precision.
