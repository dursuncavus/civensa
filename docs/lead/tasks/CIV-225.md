# CIV-225 — EK-1 listing: bulk-load the remaining per-document rows

Owner: lead (CV Lider 76). Review: Codex (GPT-6.1 Sol, high), clean on 21e63fd. Decisions: D-487 (merge recorded), D-488 (live result). Package written after the merge (D-487 noted it was missing).

## Problem (DOĞRULANDI)
- Live after CIV-224 (#523): `/activity-sections?period_id=1` ~6 s (first load 9 s), /health latency ~6–10 ms per query.
- CIV-224 left ~10 queries per document (freeze, workflow events, resource rows, section contents, assurance statements, photos, unit tables, financial entries) and ~4 per indicator once the 2026 activity report exists.

## Change
- `activity_sections_service.prefetch_listing(db, docs)`: one query per table for all listed documents (latest freeze, workflow events, resource rows, section contents, assurance statements, photos without removals, unit tables, financial entries), stored with `listing_memo.prefill`.
- `core_rows`: indicator items, bindings, definitions, latest actuals and directions in 4 queries per revision (used only inside the listing memo; outside it the per-item path is unchanged).
- Readers (`latest_release`, `resources`, section contents, workflow `events_of`/`latest`, unit photos, assurance `placed`) use the memo when it is active.

## Result
- Test fixture: 1256 → 47 queries (no indicators), 1487 → 53 (with indicators); identical report data (JSON comparison test).
- Live (D-488, 15 Nov): first load 5.0 s, then 1.4–2.5 s (5 loads, median 1.7 s); 1293 table rows, 552 KB HTML.

## Tests
- `tests/test_civ224_listing_queries.py`: same data with and without memo, `listed*10 < plain`, ≤80 / ≤90 queries; memo off outside a listing and with pending writes.
