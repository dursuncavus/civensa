# CIV-224 — EK-1 listing: read period-wide rows once per page

Owner: lead (CV Lider 76). Review: Codex (GPT-6.1 Sol, high). Decision: D-485.

## Problem (DOĞRULANDI)
- Live, after release #519 (CIV-223 per-process book cache): `/activity-sections?period_id=1` still 13–15 s (2 loads, 13 Nov 20:40).
- Local profile on the 34-document FR fixture: 1514 queries per listing (37 per directorate, 296 for İdare). Live query round trip to Neon ~6 ms → ~9 s in round trips alone. CPU (parsing) was not the bottleneck; Render Starter would not fix it.
- İdare: `approved_sources` ran 2 queries per directorate and is called 4 times per report.

## Change
- `app/listing_memo.py`: explicit request-scoped memo, active only inside `listing_memo(db)`; stops reusing as soon as the session has pending writes.
- EK-1 listing (`activity_sections_routes.listing`) runs inside `listing_memo` + one `structure_read_context`, and keeps strong references to departments, periods, organizations and users so `db.get` stays in the identity map.
- Memoized per page: İdare document, its budget rows and policy, unit document list, latest publication, unit-book publication, indicator report/revision, section definitions, department scopes; per document: financial entries (all kinds in one query) and unit tables (all kinds in one query).
- Always (not only in the listing): `approved_sources` loads unit documents and their newest approval in 2 queries; `view` derives the current status from the event list it already loads.

## Result
- 1514 → 374 queries on the fixture; identical report data (test compares JSON with and without the memo).
- Expected live: a few seconds (BELİRSİZ until measured after the release).

## Tests
- `tests/test_civ224_listing_queries.py`: same data, ≥3× fewer queries, ≤16 per document; memo off outside a listing and off with pending writes.
